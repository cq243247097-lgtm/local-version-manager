## 1. 目标与当前基线

面向 Git 新手，在独立桌面浏览器工具中管理软件源码、安装包和升级包。工具自身代码与被管理项目分开存放，通过显式配置的项目路径建立关联。

当前有独立 Git 仓库但尚无提交；所有文件未跟踪，不能仅用 `git diff` 判断实施改动。现有页面在 `frontend/`，静态入口 `preview.mjs`，执行 `npm run preview` 后访问本机 4189 端口。当前所有数据和提交/推送动作均为演示。

保留用户已认可的侧栏、颜色、卡片、目录树、分支图和详情布局。只做 PC，不重做视觉设计、不增加手机端、不迁入进销存项目源码目录。原项目中的旧演示副本保留，不再同步修改。

## 2. 协作方式与交付责任

| 角色 | 责任 |
| --- | --- |
| 用户 | 决定产品范围，提供必要路径，授权真实写入、联网及发布操作 |
| 总控 Codex | 维护总方案，每个大阶段结束后审查实际代码并总验收 |
| 阶段控制会话 | 细化阶段、拆出单任务卡交用户、验收 Gemini 各任务与阶段集成；P1 为 GPT-6 Sol / high |
| Gemini | 按阶段任务书实施、定向验证、自审、整理交接证据，停止写入后交回验收 |

Gemini 的具体型号与推理设置由用户在其环境中选择，本方案不虚构或自动修改设置。Codex 不自动连接 Gemini 账号、不配置外部 Runner、不传送仓库。用户把阶段控制拆出的单任务卡交 Gemini，由 Gemini 在同一独立项目目录实施，阶段控制先验收，总控再做大阶段验收。

同一阶段只有一个代码写入者。Gemini 开始实施后，Codex 验收前不并行修改代码；验收发现缺陷先交回 Gemini 修复。若用户要求 Codex 直接修复，应先停止 Gemini 的写入。Gemini 的“已完成”或测试摘要不等于验收通过。

## 3. 产品行为

### 源码区域

- 显示已选择项目、当前分支、未提交的变更路径数量、本地相对跟踪分支的领先/落后提交数。
- 25 格用于提醒文件改动积累，每个路径计一次；同一文件暂存和未暂存都有修改仍只计一次，重命名按一个变更记录计数。展示新增、修改、删除、重命名和冲突状态。
- 格数满后保留实际总数。颜色按现有阈值变化，颜色不代表改动风险等级。
- 本地未提交文件与未推送提交分别统计；空仓库、无跟踪分支、分离 HEAD、Git 不可用等不能伪装成“0，已同步”。
- 分支图基于真实提交的父子关系和引用，标明当前分支及本地跟踪引用。提交历史可以有限加载，并明确“仅展示最近 N 条”。
- 不联网时只能比较本地保存的远端跟踪引用，标明“本地跟踪快照，未联网核实”。本地扫描时间不当作远端获取时间。

### 安装包区域

- 从用户指定的材料根目录读取树形清单，不把材料搬进工具仓库。
- 区分目录为空、发现文件但待识别、信息不完整、完整性未检查/通过/异常、安装验证未做/通过/失败。
- 文件存在、完整性通过和安装验证通过是不同事实，不能合并为一个“可用”。
- 版本、修订、平台、源码关联、验证记录只有来源明确时才展示为已知；不得由目录名推断精确构建来源。

### 升级包区域

- 保留树形清单，右侧展示目标版本与明确声明的来源版本列表。
- 左侧版本行显示“目标版本 → 最低支持来源版本”，目录折叠后仍可见。
- 最低值只从支持直接升级的来源列表中取；不包含中间升级路径，不表示整个版本区间全部支持，不等于已实测。
- 没有声明时显示“待确认”，空目录显示“暂无升级包”。多份修订若声明不同，必须按包/修订展示，不合并成误导性的版本级最小值。
- 非正式版本、版本范围、预发布版本的比较规则在材料阶段明确；不得把当前演示的数字排序直接当成通用版本规范。

## 4. 技术框架与复用

推荐延续原生前端 + Node.js 本机服务 + 已安装的 Git CLI。现阶段不需要数据库、云端、账号体系、Electron 或框架重写。

建议职责边界：

```text
frontend/              页面、样式、视图状态、演示数据
server/                HTTP 接口与应用组合
server/git/            Git 命令调用、输出解析与领域结果
server/materials/      材料清单与声明读取（后续阶段）
.local/                本机项目配置，Git 忽略
tests/                 临时仓库、临时材料及接口验证
docs/                  方案、阶段任务书、验收记录
```

目录按实际实现需要创建，不预建空服务或通用插件系统。正式入口可新增 `npm start`，继续保留 `npm run preview` 的离线演示用途。

复用依据：

- 当前前端已获用户认可，继续复用，可把演示数据、渲染和事件按实际需要拆分，但不借机全面重构。
- Git CLI 已有权威状态、提交及引用能力；用结构化输出解析，避免自研 Git 对象存储读取。
- [Git status 官方文档](https://git-scm.com/docs/git-status)提供 porcelain v2、NUL 分隔路径和避免可选锁的说明。以机器可读格式处理中文、空格和换行路径，不解析本地化的人类输出。
- [Node child_process 官方文档](https://nodejs.org/api/child_process.html)提供 `execFile`/`spawn` 的参数数组与超时能力；禁用 shell 拼接，Windows 子进程不弹窗口。
- 本阶段无需增加第三方库。若执行者提出依赖，应说明确切解决的问题、许可证、版本维护情况与替代成本，不为封装几条命令自动安装整套框架。

## 5. 本机运行与安全边界

服务只绑定 loopback，采用同源前端；不能因为监听本机就默认任意网页均可读取本地仓库。API 校验 Host/Origin，拒绝不允许的跨域来源，不开启通配 CORS。静态资源只提供白名单文件，不能把项目根目录或 `.local` 暴露为下载目录。

项目配置存本工具 `.local`，只允许配置中的项目 ID 进入业务接口；不提供客户端任意命令或任意路径读取接口。配置路径在服务端解析、验证并由服务端建立 ID 映射。文件内容与路径作为文本渲染，不能变成 HTML 或 shell 代码。

P1 增加“接入已有项目”向导：用户主动输入路径，专用端点只读识别已有 Git 状态并显示接入摘要，确认后仅保存本工具配置。此有限路径输入不扩展到普通业务接口。完整保留现有未提交、未推送工作；不自动 git init、克隆或拉取。接入流程以实施总方案第 6 节及阶段细化为准。

真实模式的错误必须显示真实错误，禁止失败后自动回退假数据。演示模式保持醒目标记且与真实模式完全分离；模拟提交/推送只能在演示模式启用。

只读阶段不联网、不 fetch、不执行 Git 写命令，不修改被管理项目的工作区、索引、引用或配置；避免 Git 可选的索引刷新写入，不绕过 Git 所有权检查。遇到不安全目录提示说明原因，不设置全局 `safe.directory=*`。

## 7. 验收与返修

验收顺序：确认写入停止与文件清单 → 审查实际差异 → 检查必要命令/浏览器证据 → 定向复现风险点 → 给出结论。

- **通过**：阶段需求及关键边界均有证据，无阻断缺陷；未验证平台/场景明确记录。
- **返修**：列出复现步骤、预期/实际行为、具体文件和风险，由原实施者修复；只重验受影响项。
- **停止**：需要超出授权的真实写入、冻结契约变更、缺少必要输入或无法安全验证。

阶段控制先验收单任务和阶段集成，总控再独立完成大阶段验收。每层验收分两部分记录：需求是否满足；实现是否遵守范围、独立性与安全约定。提交、推送和发布需用户另外明确授权，不属于通过验收的自动后续动作。
