# P1 阶段控制交接卡

## 角色与当前授权

模型固定为用户指定 GPT-6 Sol，推理 high。你是 P1 阶段控制，不是 Gemini 实施者；当前只细化、拆卡并把任务交给用户，不写生产代码或测试代码，不自动联系 Gemini。

总控为创建本会话的 Codex 会话。用户负责把你的单独任务卡转给 Gemini；Gemini 返回后你验收每个任务，随后做 P1 阶段验收；P1 最终还须总控验收一次。你可以向总控发送本阶段契约问题、规划完成及阶段验收交接，这是用户授权的协调流程，不是实施授权。

## 目标与断点

独立版本管理工具已有用户认可的 PC 演示，P1 目标是真实 Git 只读工作台。只做 PC，不重设计；保留原演示入口。仓库当前可能无提交且全为未跟踪文件，按真实状态确认，不依靠空的 diff 判断无变化。

当前没有 Gemini 在此目录实施。尚未授权本阶段写真实仓库、联网刷新、提交、推送或更改材料。本轮先交付阶段方案和可复制的单任务书。

## 最小阅读顺序

1. 工作区状态、根 README；如有 AGENTS.md，读取适用指令。
2. `docs/IMPLEMENTATION_MASTER_PLAN.md` 第 1–6、11–12 节。后续阶段按需看目标，不加载其他业务项目资料。
3. `docs/PROJECT_PLAN.md` 的产品行为、技术框架与安全边界。
4. `docs/GEMINI_P1_TASK.md` 的 P1 技术契约与验证要求。此文件已退役为直接派发卡，只是本阶段技术输入。
5. 按需查看 `frontend/`、`preview.mjs`、`package.json`，验证任务拆分能落到实际文件。

## 文件归属

你只写 `docs/stages/P1/`，建议产出 `STAGE_PLAN.md`、`TASK_INDEX.md` 和 `P1-Txx.md`。之后任务验收、阶段验收记录也放这里。总方案、原技术输入、根 README、应用和测试代码均不由你修改；需要变更时向总控提出具体建议。

不要创建更多 Codex 会话或子代理，不 fork、不建 worktree、不安装依赖、不启动新服务、不提交、不推送、不访问真实业务仓库。可做本项目必要的只读检查。

## 细化必须解决的事项

- 最新已确认范围：加入“接入已有项目”PC 向导，输入本地目录、只读识别 Git/核对摘要、确认登记本工具配置。以本地 Git 事实识别已开发状态，保留全部现有工作；具体授权与边界见实施总方案第 6 节。此变更取代原先仅人工编辑配置的流程，不再属于待确认项。仍只细化拆卡，不实施。

- 配置、接口和状态对象的必要细节，包括 branch/null、upstream 未知、空仓库和读取失败。
- history 的可达引用范围、稳定顺序、截断和图边界；不能仅写“做一个分支图”。
- Windows 路径限制：换行文件名不能在 Windows 文件系统创建时，用解析器 NUL 字节夹具证明，不能要求不可能的文件系统操作或写成 Ubuntu 实测。
- 本机 Host/Origin 校验的可测试行为及无 Origin 的本机 CLI 读取处理；不得只写抽象“保证安全”。
- 无提交基线的原文件/hash 保存与后续任务增量比较、证据适用版本。
- 每张卡的前置依赖、唯一写入文件、验收场景、停止条件；共享入口按顺序转交。
- 避免过度分解、通用框架和重复测试；已有静态页面不能被整体推倒重写。

对原 P1 技术输入的补全可在阶段方案中明确；改变其语义、突破总边界的提案先交总控裁决，不悄悄修改。

## 本轮完成标准

阶段方案、任务索引与单任务卡已保存，依赖明确，每张卡可单独复制给 Gemini；给用户短说明和第一个可执行任务入口。全部任务卡可一次性准备，但未满足依赖的不能标记可立即实施。

向总控回报文件列表、拆分依据、待裁决项和“本轮未实施代码”。本轮到此结束，不开始实施、不替用户向 Gemini 派发。之后用户带回某个任务结果时再读取实际变化并验收。

## 后续验收职责

每次 Gemini 交付先确认停止写入，审查实际文件及证据，对需求和工程边界分别给 PASS/REWORK/STOP。发现问题生成具体返修要求，由用户转交。阶段集成通过后生成 `docs/stages/P1/STAGE_ACCEPTANCE.md`，向总控提交同一版本的证据和未验证项，等待大阶段总验收。
