# 材料格式统一方案：制作时生成记录，旧包一次性补旁路记录

日期：2026-09-28。总控已在 [P2 统一材料记录路线裁决](../../P2_FORMAT_DECISION.md) 中选择本方案；依据用户对旧包数量和未来统一方式的补充、[真实来源盘点](REAL_SOURCE_INVENTORY.md)及当前 [材料记录 v1](MATERIAL_RECORD_V1.md)。这是后续实施方案，尚未改写真实材料。**真实根目前只有查看授权，不能提前写入。**

## 选择

**以材料根级 `material-records.json` 为统一读取格式。** 现有 P2 已能解析它；旧材料只有两份安装包 ZIP、一份升级候选 ZIP，可一次性补两份旁路记录（安装包根一份、升级包根一份），保留原 ZIP、`release-record.json`、`SHA256SUMS.txt` 和说明原字节。不要为三份旧包长期维护一套独立的旧格式解析器。若未来确有大量不能迁移的只读归档，再评估受限旧格式适配器。

## 将来的记录由谁生成

1. **Git 提交只确定源码检查点**。一次提交可能没有生成包，一个包也可能涉及多个构建输入；提交时不能凭提交本身填包文件名、哈希、安装验证或升级兼容。
2. **实际制作包的脚本/流水线是记录生产者**。构建成功后从输出文件取得相对路径、实际大小和 SHA-256，连同明确传入的版本、修订、平台、源码检查点，生成或原子更新 `material-records.json`。默认状态为“候选”；缺信息写 `null`/不写字段并阻止伪造“通过”。AI 可以调用脚本、检查证据、草拟说明，但不能手填、猜测或替代构建与测试事实。
3. **安装/升级验证是另一事件**。只有执行了明确的测试并保留环境、时间和结果证据，才追加相应历史验证记录；未测保持“未验收”。升级包 `directFrom` 仅从明确声明的精确来源版本列表产生，不能从包名 `rc9-to-c4` 猜一个可比较的最低版本。
4. **本管理软件是读取与核对者**。日常接入项目或材料目录时只读，绝不自动初始化、改写目录或重做包。未来可在材料归档阶段提供“为旧包生成草稿”动作：明确点击后展示待写文件、字段来源与未知项，用户确认后单独写入；这属于受控归档功能，不混进 P2 的 GET/关联向导。

## 旧包一次性归一

- 只新建 `安装包区/material-records.json` 和 `升级包区/material-records.json`，分别引用现有三个 ZIP 的根内相对路径。版本、修订必须能追溯到现有 `release-record.json`、`release-notes.md` 或 `*source-link.json`；不能把源码整合检查点冒充安装包唯一构建提交。
- 三份材料均标“候选”。已有 `assets[].sha256` 只可作为**历史登记摘要**，本次不重算，不转成 `integrityRecord.result:'passed'`；已知文件大小相符也不能证明字节完整性。安装/升级验证无已通过证据，保持未验收；升级 `directFrom` 留空值/省略，含义为未知，不写 `[]`（明确无直接来源）。
- 当前 v1 缺候选状态与“登记摘要”展示字段。[P2-T04](P2-T04.md) 先增加向后兼容的可选字段，并在 API/前端显式标“候选”“历史登记 SHA-256，本次未核验”。旧 v1 文件仍可读取，未知字段继续白名单过滤。先在工具工作区生成两份完整草稿、逐字段来源、精确目标路径与影响清单；用户确认具体内容前不写真实根。若目标已存在，先比较并报告，不覆盖。

## 验收关口

T04 用小型假包验证字段读取、来源、错误与展示，用真实目录只读核对草稿引用和大小。未来实际打包脚本的生成、幂等更新、冲突、原子替换与失败清理另立后续任务，不在 T04 实施。若用户之后确认一次性迁移，再比较旧文件指纹并确保只新增两份记录文件；浏览器核对候选/未验收/未知兼容的显示。P2 阶段最终 PASS 仍须真实模式复验与总控独立验收。本方案不自动启动 P3/P4。
