## S1（高）：Git 只读调用不得执行 fsmonitor

当前 `runGit()` 的调用边界没有关闭仓库配置的 `core.fsmonitor`。总控在隔离仓库设置无害监控脚本后，调用真实 `getRepositorySource()`，脚本实际写入 `.git/review-monitor-ran`。修复须使接入检查及普通源码读取均不会执行该脚本，并维持已有禁交互、外部 diff、可选锁、超时和输出上限边界。应在**本次 Git 子进程调用边界**施加可靠的禁用设置，不修改用户仓库、本机或全局 Git 配置，也不通过删除夹具中的 fsmonitor 配置绕过复现。

在系统临时目录创建真实 Git 仓库，给仓库配置指向会产生标记文件的无害 fsmonitor 脚本；分别调用 `inspectRepository()`/接入检查与 `getRepositorySource()`/源码读取，断言成功读取、标记文件始终不存在，并比较调用前后工作区文件、`.git/index`、refs、`.git/config` 及其他 Git 文件的内容/存在状态。保留原本正常的未跟踪、暂存和未暂存状态计数。若其他已约定的 Git 外部执行入口可在这些只读命令上触发，也在同一调用边界关闭并给出定向证据；不得扩大为修改业务仓库的配置。

## R1（中）：本地上游不冒充远端待推送

总控夹具中 `main` 跟踪本地 `baseline`，无任何 remote；API 返回 `upstream.state=available`、`name=baseline`、`ahead=1`、`behind=0`，但页面显示“待推送提交”“远端跟踪”。优先将可用上游的标题、阶段、数字标签、说明及顶部帮助文案改成不超出接口证据的“上游分支 / 领先提交 / 本机快照”等中性表述；若保留远端专用文案，必须有可靠的引用类型依据，不能仅凭名字有无斜杠猜测。`ahead/behind` 数值口径不变，未配置/不可用上游仍显示未知或无上游，不伪装 0/已同步；不执行 fetch。

用两个隔离仓库状态做浏览器验证：本地分支上游且没有 remote、以及本地保存的远端跟踪上游。核对页面各处文案、领先/落后数字、未联网提示和刷新后的状态；本地分支场景不得声称有远端或待推送提交。

## R2（中）：按错误来源重试

首次 `GET /api/projects` 因损坏配置失败时，页面显示 `CONFIG_INVALID`，但“重试读取”仅在 `currentProjectId` 非空时调用项目读取，因此修复磁盘配置后点击没有新请求。为错误状态保留明确来源：**项目列表加载错误**重试 `reloadProjectsList()`，**已选项目 source/history 错误**重试该项目读取；不要只用 ID 是否为空分流。已有选中项目后列表加载失败也必须重试列表。服务暂时不可用时保留输入/选择与真实模式，不回退演示、不显示假成功。

浏览器定向验证：隔离配置先写损坏 JSON，加载得到 `CONFIG_INVALID`；修复配置后点“重试读取”，实际发起新的列表请求并进入空态或合法项目工作台，无需整页刷新。再覆盖“已有选中项目但列表重载失败”与“项目 source/history 失败后恢复”，确认各自请求路径、错误消息和成功状态；临时服务断线恢复时按钮也可重试。对旧请求与项目切换的防覆盖行为做最小回归。
