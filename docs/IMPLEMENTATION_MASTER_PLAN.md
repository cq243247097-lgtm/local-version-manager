# 版本管理工具：多阶段实施总方案

版本：2026-09-28 / v3。本文是阶段划分、协作责任、推进与总验收的权威入口；产品语义与技术依据见 [项目方案](PROJECT_PLAN.md)。发生冲突时以用户最新要求、本文、阶段细化、单任务卡的顺序处理。

最新进度与流程：P1/P2 已总控 PASS，用户已要求新建 GPT-6 Sol / high 会话主控 P3，见 `P3_STAGE_CONTROL.md`。P3 由其拆卡交用户转 Gemini、逐卡审核，小规模 Bug 可在单一写入者条件下直接修复；中间不例行向总控汇报，只有架构偏差协调，阶段完成后统一交总控审核。此约定覆盖下文旧版通信与禁止阶段控制直接修复的限制。

当前进度：P1 总控最终 PASS，见 [P1 最终复验](acceptance/P1_R01_FINAL.md)。用户已要求开始 P2，现进入阶段细化与拆卡，沿用现有 Sol / high 阶段会话；输入与边界见 [P2 阶段交接](P2_STAGE_CONTROL.md)。旧文中的 P0 基线为历史起点，不代表当前实现状态。

## 1. 目标、基线与总边界

交付独立于被管理项目的 PC 本地版本管理工具：源码区可理解 Git 状态与版本关系；安装包区能区分材料存在和验证程度；升级包区显示明确兼容来源与最低支持箭头。保留已经认可的 PC 视觉布局，不做手机端。

当前 P0 完成：独立目录、独立 Git 仓库、演示前端和本机预览入口。当前仓库无提交，文件未跟踪，真实后台尚未实现。原业务项目中的演示副本保留，不再作为开发目录。`npm run preview` 是模拟页面，不是正式管理服务。

全程不把工具源码写入被管理项目，不自动提交、推送、联网同步、部署、发布或启用调度。不开发自动升级执行、恢复生产、后台代理或外部 Runner。允许在临时夹具中模拟真实操作，不能把测试授权扩展到真实仓库和材料。

## 2. 四层分工

| 层级 | 执行者 | 工作与输出 |
| --- | --- | --- |
| 总控 | 当前 Codex 会话 | 维护总方案、必要跨阶段约定，每个大阶段完成后审查实际代码并总验收 |
| 阶段控制 | 单独 Codex 会话；P1 指定 GPT-6 Sol / high | 细化一个阶段、拆成可独立交给用户的任务卡；验收 Gemini 每个任务及阶段集成 |
| 实施 | 用户选择的 Gemini | 只实施收到的任务卡、验证并回报；不替自己判定阶段验收通过 |
| 用户 | 用户本人 | 接收单任务卡、转交 Gemini、带回结果，决定范围变化与真实外部/写操作授权 |

阶段控制会话不直接开发代码，不自动派发 Gemini，不自行创建更多实施会话。当前授权新建一个 P1 阶段会话；后续阶段沿用相同流程，进入时再指定阶段会话，不提前批量创建。

阶段控制可与总控沟通本阶段进度、契约问题及验收交接；不能把此协调授权解释为自动调用 Gemini、代替用户转交任务或自动进入下一大阶段。阶段控制验收不能替代总控的大阶段验收。

## 3. 工作顺序和两级验收

1. 总控给出大阶段目标、边界、输入、完成标准，交给阶段控制。
2. 阶段控制核对真实工作区，生成阶段细化方案、依赖顺序、单任务卡索引；把尚有实质歧义的契约单独列出，不交给 Gemini 随意决定。
3. 用户取得阶段细化及单任务卡。任务有依赖时依次转交；未解除依赖的任务明确标为待解锁。无必要不拆太碎。
4. Gemini 按一张卡实施，交回文件清单、命令和结果、截图/夹具证据、未完成项，停止写入。
5. 阶段控制读取实际文件和变化，复核需求及范围，给出 PASS / REWORK / STOP。REWORK 交用户转回同一实施任务修复，直到该任务通过。
6. 阶段内任务通过后，阶段控制检查联动行为、更新阶段验收记录，给出阶段级结论并停止写入，交总控。
7. 总控审查该阶段真实差异与证据，定向验证集成和关键风险。总控 PASS 后该阶段才关闭；REWORK 返回阶段控制组织修复。总控不得只签收下级摘要。
8. 下一大阶段由总控基于通过版本准备任务，不允许 Gemini 凭路线图连续实施后续阶段。

通过验收不自动产生 Git 提交、推送、部署或发布。用户没有授权这些动作时保留未提交状态。

## 4. 文件归属与证据基线

- 总控独占：本文、`docs/PROJECT_PLAN.md`、`docs/P1_STAGE_CONTROL.md` 和 `docs/acceptance/` 下的大阶段总验收记录。
- 阶段控制独占：`docs/stages/Pn/` 内的阶段方案、任务索引、任务卡、任务验收与阶段验收记录。根 README 的当前文档入口由总控维护；实施带来的使用方式变化可在指定任务内分配唯一 Gemini 写入者。
- Gemini 独占：当前已发任务卡指定的实现、测试与对应交付记录；每张卡列出允许路径和不可修改路径。共享文件按依赖顺序转交，不能两个任务同时写。
- 任务验收期间 Gemini 停止写入；阶段验收期间所有实施者停止写入。若发现外部变化，先核对证据适用版本，不覆盖他人变化。
- 无提交基线时，在 `.local/baselines/` 保存必要原文件副本与相对路径/hash 清单；每次交付记录新增、修改、删除。基线不能混入凭据或业务数据，不复制整个其他仓库。总控和阶段控制据原件与当前版本比较，而非依赖空的 `git diff`。
- 测试证据可复用同一待审版本的有效结果。只有新变化、失败或具体疑点才补充验证，不按层级重复跑全套。

## 6. P1：真实源码只读工作台

**输入**：当前前端、静态预览、产品语义，以及 [P1 技术输入](GEMINI_P1_TASK.md)。旧单包任务书改为阶段控制的技术输入，不能再整包直接派给 Gemini。

**已确认的接入范围（2026-09-27 补充）**：增加“接入已有项目”PC 向导，用户输入本地目录 → 只读识别 Git 仓库并核对根目录、历史及未提交/未推送状态 → 确认后仅登记本工具 `.local/projects.json` → 进入工作台。以本地 Git 事实为主，不以远端覆盖本地，完整保留已开发一半的工作。无 Git 的目录提示本阶段不支持，不自动初始化；克隆、fetch/pull、切换分支与其他 Git 写操作均不属于 P1。材料关联可稍后进行。

接入检查/确认端点是接收用户主动输入路径的唯一有限例外；普通业务接口仍只接收已登记 ID。阶段控制细化路径归一、重复登记、配置保存失败和并发确认语义，保护旧配置，明确同源/抗跨站策略。P1 的“只读”针对被管理项目；允许接入确认写本工具配置。验收补充已开发仓库接入不丢改动、取消不登记、重复不重复、重启登记保留和保存失败不丢旧配置。

**结果**：本机配置所登记的项目可以在 PC 页面切换；源码状态、文件列表、真实提交关系与本地跟踪引用可见。未配置、空仓库、无上游、冲突、读取失败和历史截断有真实提示。演示与真实模式分开，真实模式不运行模拟提交/推送，材料区仍明确为演示。

**需要细化的契约**：配置校验和 ID 规则；响应对象、错误、超时/输出边界；历史查询引用范围与图布局；Host/Origin/同源策略；临时夹具和证据基线。保持只读、不联网、不 fetch，不改被管理项目索引、引用、配置和文件。

**建议拆分方向**：配置与服务骨架、Git 读取与解析、真实历史图/前端接入、阶段联动验收。只是可选拆分方向；阶段控制根据共享文件与依赖选择最小任务数，不能为了凑任务数量设独立机械阶段。

**验收出口**：状态/计数真实、未知不等于零；文件名边界正确；分支图父子引用正确；前端无假数据回退；临时仓库读取前后无写入；本机接口不暴露任意路径；现有 PC 外观保留。Windows 实测，其他平台证据如实标注。

## 7. P2：材料只读资料库

**输入**：P1 通过版；用户显式提供的材料目录；只读材料格式盘点。不得假设旧目录有 manifest，不读取整份业务源码。

**结果**：两个材料区从真实目录显示版本、修订、文件、大小、来源和已登记验证记录；空目录、无法识别、信息不完整与读取失败分别显示。升级最低版本从明确支持列表得到；同一版本多个包/修订声明不同须分开显示。

**进入前契约**：选用何种材料记录来源，缺失/冲突信息怎样显示，版本比较和预发布标识规则；目录遍历边界、符号链接处理、扫描范围与截断提示。优先适配现有材料，不在只读阶段生成或改写旧记录。

**建议任务方向**：材料识别契约与样例 → 扫描/记录适配 → 两区真实接入与阶段验收。

**验收出口**：夹具含空目录、未知文件、缺失声明、冲突记录、不同修订的兼容差异。文件存在不等于安装通过，来源未知不伪装精确源码关联，最低支持摘要与详情同源一致；扫描前后材料不变，不运行包内容。

## 8. P3：人工 Git 操作

**输入**：只读视图稳定、用户明确选定首批写操作。候选为本地提交、推送、刷新远端跟踪信息、创建/切换分支；具体操作逐项冻结，不默认全做。

**结果**：新手在页面明确看到操作对象、影响范围、未提交文件处理和结果；只有主动操作才执行。联网刷新必须与本地刷新区分。

**进入前契约**：提交文件选择与已有暂存内容、Git hooks/签名与凭据交互、并发仓库变化、分支切换未提交内容、非快进推送与失败后实际状态、确认后状态变化的处理。禁止偷偷 stash、reset、clean、force push 或覆盖变更。

**建议任务方向**：先冻结单操作输入/确认/结果 → 在临时仓库及本地 bare remote 实现与验证 → 前端接入 → 阶段验收。真实远端验证需另获明确授权，不能以登录态自动授权。

**验收出口**：成功/失败/取消路径真实，重复点击不重复触发并发写入；失败后重新读取状态，不回报虚假成功；无未经允许的丢改动、覆盖和强推；只读功能回归通过。

## 9. P4：材料校验与受控归档

**输入**：P2 材料契约、用户确认的写入根目录和操作范围；若已有独立可用归档工具，先评估调用或适配，不依赖原项目内部未稳定脚本。

**结果**：人工触发的完整性校验可展示真实结果；需要时支持材料导入/归档并记录来源、版本、修订、摘要。安装验证仍只展示实际证据，不能通过文件哈希推导。

**进入前契约**：重复材料、同名冲突、落盘记录、部分失败、磁盘不足、校验期间文件变化与重试；是否只写本工具记录或写归档目录。自动删除、覆盖旧包、移动唯一副本不纳入默认范围。

**建议任务方向**：真实校验 → 非覆盖归档与记录 → 界面联动 → 失败场景及阶段验收。临时材料验证为主，不使用唯一真实材料试错。

**验收出口**：校验与文件变化一致；重复导入与冲突行为明确；失败保留原始材料且结果可解释；升级兼容声明不因导入自动编造。没有授权的云端备份/上传保持未实现。

## 10. P5：独立交付与整体验收

**输入**：已通过阶段与明确裁剪清单。确认交付形式：源码 + Node 启动入口是最低交付形式；桌面安装包是可选决策，不能自行引入 Electron 或自动安装环境。

**结果**：清楚的启动/停止、配置、日常操作、错误排查与边界说明；演示和真实入口可区分；工具迁到另一个目录仍不依赖原项目位置。

**建议任务方向**：运行入口和配置体验整理 → 用户操作说明 → 临时项目端到端验证与总体交付记录。只对真实变动安排测试，不设重复验收流水线。

**验收出口**：离开开发目录仍可按说明运行；配置/材料/源码分离；安装包如纳入则另有安装与卸载证据；PC 主要流程可用；明确环境、已知限制和未验证项。Ubuntu 无环境则不宣称支持验证完成。提交、发布、打标签仍由用户授权。

## 11. 单任务卡必填内容

每张卡必须独立可复制给 Gemini，含：目标与非目标、前置任务及通过证据、文件所有权、必要契约（直接写入，不只叫人读全部文档）、实施边界、验证命令/必要场景、交付文件位置、停止条件。写明 Gemini 型号由用户选择，阶段验收者和总验收者是谁。

任务编号统一 `P1-T01` 等。阶段控制维护索引中的待执行/实施中/待验收/返修/通过/停止，不靠聊天记忆。用户转交时使用明确任务编号；单卡通过不允许自动解锁未通过依赖。

## 12. 阶段交总控的最小交接

提供阶段目标及完成差量、任务卡与验收索引、实际变化文件清单、基线/最终文件指纹、验证环境与结果、未验证项、已知风险和阶段结论；附“所有实施写入已停止”。总控取同一工作区实际文件审查，不接受仅截图或口头“全部通过”。

大阶段记录保存到 `docs/acceptance/Pn_FINAL.md`，由总控独占写入。未通过前不更新为已交付或进入下一阶段。
